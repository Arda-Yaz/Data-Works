# DataWorks acceptance gap map

Date: 2026-10-26. Scope: Phase 1, evidence and acceptance definition.

The user selected this target: an operations analyst at a small online retailer prepares a monthly order-fulfillment report for an operations manager and dashboard. This document maps the current working tree to that job. The parent acceptance matrix owns case identifiers; requirements below use descriptive names to avoid conflicting identifier schemes.

**The new fulfillment acceptance cases are not implemented or verified yet.** Source inspection, an existing test definition, a passing regression baseline, independently reproduced fulfillment output, and release readiness are separate evidence states.

Phase 1 permits documentation, attributed synthetic fixtures, declared expected outputs, and baseline verification of existing code. Phase 2 establishes execution contracts only after the user's approval. Production implementation and workspace redesign are outside this phase. Existing staged, unstaged, untracked, and deleted files are pre-existing work and must be preserved.

## Selected workflow and boundaries

The input fields are `order_id`, `line_id`, `order_date`, `sku`, `quantity`, and `fulfillment_status`. The business key is `(order_id, line_id)`; source-row identity is separate from that key.

The first workflow must establish these declared behaviors:

- Preserve order/line identifiers as text, including leading zeros. Do not infer identifier meaning from apparent numeric content.
- Parse dates using explicit formats and compatibility rules; never guess day/month order. Specify canonical date output and preserve original values as evidence.
- Normalize SKU/status through ordered, saved text transformations and exact mappings. Validate statuses after applicable mappings.
- Accept quantities only under the positive-integer rule. Missing, fractional, nonnumeric, zero, and negative quantities need explicit invalid-row outcomes. **Never impute quantities.**
- Distinguish exact repeated records from conflicting records sharing the business key. Quarantine redundant exact duplicates under a declared retained-record policy, linking them to the retained source row.
- Block an attempt containing conflicting duplicates rather than silently selecting a winner. This proposed safe policy must be explicit in the accepted contract.
- Produce accepted rows, quarantined rows with reasons, and reconciled reporting outputs. Preserve prior committed results after a blocked or failed attempt.

Month A defines the synthetic source, saved plan, and independently declared expected outputs. Month B challenges reuse of that unchanged plan. Month C has separate schema-drift, invalid-record, and conflicting-duplicate scenarios so their policies can be judged independently.

Synthetic fixtures establish an engineering specification. No actual operator, customer files, time baseline, or confirmed dashboard/export contract has been supplied. Report layout, consumer schema, status totals, and supported export format remain to be confirmed.

Statistical imputation and outlier deletion are **not transformations in this fulfillment job**. Preserve their existing behavior and record reuse risk separately; do not add median filling or quantity-based outlier removal to make fulfillment acceptance pass.

### Existing statistical-feature reuse risk (outside first-job transformations)

G04 is retained as an existing-feature risk rather than a fulfillment transformation: [backend/operations.py](../../backend/operations.py), lines 249–261, recomputes missing/outlier builders on the supplied frame. Recipes lack an explicit frozen-fit/refit contract and persisted learned fill values/bounds. Do not claim these features are safely reusable across files without their own policy and evidence.

Future statistical work must declare operation order, fitting scope, learned values, undefined-statistic behavior, and precision, and test changed-distribution files. Preserve the same-base batch behavior at [backend/cleaning.py](../../backend/cleaning.py), lines 558–614. None of this authorizes imputation or outlier deletion in fulfillment reporting.

The replay boundary also needs attention in Phase 2: [backend/operations.py](../../backend/operations.py), line 291, imports `_prepare_dataset` from the Streamlit-backed state module. Shared preparation belongs behind a UI-independent execution boundary; the UI adapter should retain responsibility for session commitment. This is a source-level coupling observation, not a claim that existing replay executes widgets.

## Product and release unknowns

1. **Real operator and measurable value:** the analyst/retailer/manager scenario is selected, but there is no observed operator, customer workflow, current time/effort measurement, or demonstrated improvement. Synthetic success is not evidence of recurring demand.
2. **Customer files and permission:** real Month A/Month B equivalents and consumer-judged expected outputs remain unavailable. Label synthetic fixtures and provenance clearly. [DEPLOYMENT.md](../../DEPLOYMENT.md), line 55, says the bundled CSV's upstream provenance/license is unestablished; no rights or representativeness follow from its presence.
3. **Dashboard/report/export contract:** confirm consumer import format, output columns/types, status semantics, report-period handling, aggregation rules, filename/encoding conventions, and use of quarantined records. No universal dashboard compatibility claim is justified yet.
4. **Policy details:** approve explicit date formats, SKU/status transformations/mappings, unknown-category handling, invalid-cell quarantine rules, duplicate equality/keeper policy, and the proposed conflicting-key block. Record policy changes as plan versions rather than implicit widget state. Quantities remain unimputed; outlier deletion is excluded.
5. **Persistence and recovery scope:** confirm whether retained `.dataworks` downloads satisfy the initial requirement; define restart loss and bounded undo expectations. Current sessions are not durable server storage; autosave/server recovery needs separately approved scope.
6. **Workload and release environment:** name sizes, hardware, runtime/memory ceilings, concurrency, and local versus private shared hosting. Existing caps are not measured guarantees. Shared use requires real OIDC/proxy/TLS checks in the target environment under [DEPLOYMENT.md](../../DEPLOYMENT.md), line 47.
7. **Distribution:** choose project licensing and confirm fixture rights before publishing. Engineering acceptance, deployment readiness, and commercial validation remain distinct gates.

## Phase boundary and release decision

Phase 1 concludes with reviewable fulfillment scope, documentation/fixtures, recorded regression baseline, and explicit unknowns. It implements no new fulfillment acceptance cases and establishes no production-readiness claim. Pause for user approval before Phase 2.

After approval, Phase 2 defines the versioned execution/persistence contracts and executable acceptance checks. Subsequent implementation extends existing preparation, replay, state commitment, and archive code. Later phases prove one complete workflow, held-out reuse/recovery, workspace behavior, workload limits, and independent reproduction. Release remains blocked until the applicable acceptance evidence and target-deployment checks are complete.
